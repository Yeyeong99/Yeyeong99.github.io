# Why I Adopted SDD to Keep AI Coding on Track and Trace Problems

The hardest part of coding with AI was not implementation speed. It was figuring out whether the code being generated so quickly was still heading in the direction I originally intended.

I would start with a clear problem. But as design discussions and implementation progressed, features and structures I did not immediately need would naturally find their way in. Each suggestion sounded reasonable: a more flexible architecture, room for future expansion, or an edge case worth preparing for.

Yet as I accepted these suggestions one by one, the design would grow beyond the original problem. Sometimes, the problem I actually wanted to solve still had not been addressed as intended.

I also struggled when the implementation diverged from the design. Code changes quickly during AI-assisted development. Even when I knew something was wrong with the result, it was difficult to identify where things had started going off track.

I lacked the evidence to distinguish between a flawed design, an implementation that had departed from it, and requirements that had changed along the way.

That is why I adopted Spec-Driven Development (SDD). **I wanted a clear reference to keep the work from drifting, and a record I could return to when something went wrong.**

## What I Expected from SDD

1. **A clearer scope of work**

   I decided to define functional requirements (FRs) and non-functional requirements (NFRs), then use them as the basis for design and implementation. Whenever AI suggested a new structure or feature, I had a question to ask first:

   “Which FR or NFR does this help satisfy?”

   If that question was difficult to answer, I could reconsider whether the suggestion belonged in the current scope. If a new requirement was truly necessary, I could add it to the specification and continue designing against the updated requirements. This helped reduce the number of conversational suggestions that slipped into implementation without proper review.

2. **Traceability**

   I expected documented requirements, designs, and reasons for changes to give me a reference when implementation results differed from expectations. I wanted to be able to check what behavior had been intended and which decisions had led to the current structure.

## What Actually Changed: Less Design Drift

The first benefit I noticed was that the design drifted less often.

Using the defined FRs and NFRs as the single source of truth for requirements gave design discussions clearer boundaries. Before designing something outside those requirements, I had to define and add the relevant requirement first. That made “Do we need this now?” a necessary question.

Previously, I had relied on intuition to decide whether to accept each plausible suggestion. After adopting SDD, I could check which requirement supported it. It became easier to push back on designs whose necessity I could not explain.

I already understood the importance of design, but as I started coding with AI, I sometimes found myself drifting away from it. For me, the key to adopting SDD was continuing to make decisions based on the design and consistently tracking clear criteria throughout the AI-assisted coding process.

## Tracing a Communication Problem Between Containers

I experienced the value of traceability while fixing a problem where communication between containers had been implemented differently from the design.

When I reviewed the implementation, I found that the containers were communicating in a way that did not match the original design. In situations like this, I would usually fall into one of two patterns:

1. Spend time searching through history or trying to remember whether the design had changed without my noticing, and whether the implementation reflected that change.
2. Focus only on the current code and errors while trying to determine whether the design itself was flawed, then patch the immediate behavior and move on.

This was where the documents produced by the SDD workflow proved useful. By comparing the documented design with the actual implementation, I could trace how communication between the containers was supposed to work and where the implementation had diverged. Those records helped me identify the cause and correct the relevant part.

SDD had not prevented the implementation error. The implementation still departed from the design. What mattered was that I had a reference to return to and a record that helped me trace the cause.

It also gave me a clearer basis for asking AI to make corrections. Instead of vaguely saying, “Communication is broken—fix it,” I could use the documented design to explain what had diverged and what needed to align.

## What I Value About SDD Today

I have not yet evaluated SDD’s impact quantitatively. But two benefits have become clear through my experience so far.

First, it has become easier to keep the work within scope by referring to FRs and NFRs. Second, when the implementation departs from the intended behavior, I can follow the documentation to trace the problem.

With AI-assisted coding, code is generated so quickly that it is easy to lose track of why it was written that way. For me, SDD has been a way to preserve the reasoning behind requirements and design while working at that pace.

Implementations will continue to diverge from designs. I use SDD because it gives me a basis for assessing those differences and figuring out where to start fixing them.
