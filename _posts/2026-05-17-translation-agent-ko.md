# 레거시 번역 코드에서 문서 단위의 일관성까지: 번역 파이프라인에 메모리를 더한 과정

근무하던 기업에서 B2C 서비스로 업무에 특화된 에이전트 그룹을 개발하기 시작했다. 그 과정에서 나는 번역 에이전트 개발을 맡아 UI 기획부터 Agent 개발 및 개선을 맡았다.

문서를 번역하는 기능을 개발하면서 처음 출발점으로 고객사에서 사용하던 번역 에이전트를 참고 하였다. 기존에 동작하던 흐름을 활용하면서 작게나마 개선시키고자 했다.

고객사의 번역 에이전트는 이미 문서의 텍스트를 잘 추출하고, 번역 결과를 원래 위치에 돌려놓는 일을 잘 수행해내고 있었으므로, 내가 집중했던 문제는 같은 용어가 다르게 표현되거나, 앞부분과 뒷부분의 문체가 어긋나는 식의 일관성 문제였다.

이 글에서는 이 문제를 consistency, 즉 **문서 전체에서 번역 판단의 일관성을 유지하는 문제**로 보고, 파이프라인에 사전 분석과 메모리를 추가한 과정을 정리한다.


## 1. 번역에서 필요한 맥락을 함께 모델에 넘겼다

문서 번역은 Doc2Doc 이었기 때문에 단순 번역 모델 호출 외에도 처리할 일이 많았다. 단건 번역에 비해서 맥락을 유지하는 일이 관건이었다. 그래서 처음에는 번역을 하고자 하는 페이지 외에 앞, 뒤 페이지를 함께 LLM 모델에 넘기는 식으로 번역 때 참고할 만한 맥락을 알려주었다. 

하지만 이렇게 근접한 페이지를 넣기만 해서는 200 페이지 가량 되는 장문의 문서에서는 1페이지와 140페이지의 같은 단어가 같은 뜻으로 번역될 지 보장할 수 없었다.

## 2. Consistency를 용어와 문맥으로 나누어 보았다

프롬프트에 근접한 맥락을 부여하는 것만으로는 모자랐다. 그래서 장문 번역에 대해 조사를 하였고, 최종적으로 아래 두 가지 논문을 참고하여 번역 에이전트의 설계를 개선했다. 

- [DelTA: An Online Document-Level Translation Agent Based on Multi-Level Memory](https://arxiv.org/abs/2410.08143): 다층 메모리와 이중 언어 요약을 활용하는 문서 번역 연구.
- [Translating Step-by-Step: Decomposing the Translation Process for Improved Translation Quality of Long-Form Texts](https://aclanthology.org/2024.wmt-1.123/): 사전 조사부터 교정까지 번역 과정을 단계로 분해한 연구.

논문의 내용을 토대로 consistency 문제를 두 가지 관점으로 나누어 접근했다.

- 첫째는 **용어의 일관성**이다. 같은 의미로 쓰인 용어라면 문서 안에서 동일한 번역 기준을 따라야 한다. 약어와 정식 명칭의 관계, 비슷해 보이지만 구별해야 하는 개념도 여기에 포함된다.

- 둘째는 **문맥과 문체의 연속성**이다. 앞에서 설명한 대상을 뒤에서 어떻게 지칭하는지, 논의가 어느 단계까지 진행됐는지, 제목과 본문에서 어떤 문체를 사용하는지 이어져야 한다.

예를 들어 같은 의미의 용어를 앞에서는 ‘입금 처리’, 뒤에서는 ‘예금 처리’로 옮겼다면 용어 관리가 필요하다. 반면 뒤 문장의 ‘이 절차’가 앞의 어떤 설명을 가리키는지 놓쳤다면 담화 문맥이 필요하다. 두 문제에는 서로 다른 정보가 필요했다.

## 3. 번역 전에 문서의 용어와 의미를 먼저 정리했다

용어 일관성을 위해 먼저 도입한 흐름은 용어 스캔과 사전 분석이다.

```text
문서의 번역 단위 수집
  → 용어 후보와 원문 근거 수집
  → 사전 분석
  → 문서 용어 메모리 초기화
  → 실제 번역에 관련 정보 주입
```

이 과정에서 각 데이터의 역할을 구분했다.

| 구성 요소 | 역할 |
| --- | --- |
| Temporary Glossary (용어집) | 원문에서 수집한 용어 후보와 근거 보관 |
| Pre-Translation Analysis (사전 분석) | 원문을 바탕으로 문서의 의미와 용어 관계 분석 |
| Document Term Memory (용어집 업데이트) | 번역에서 참조하고 이후 갱신할 활성 용어 상태 관리 |

이때 용어집의 경우 n-gram과 같은 방식을 이용해 자주 나오는 단어들 위주로 수집하였고, the, a, an 같은 의미 없는 관사는 제외하도록 했다. 이렇게 수집한 단어는 해당 단어를 포함한 문장들과 함께 1차적으로 LLM에 넘겨졌으며, LLM은 문장을 토대로 어떻게 용어를 해석해야하는지 결정했다.

또한 사전 분석의 경우, *Translating Step-by-Step*의 방법론에서 착안했다. 문서의 도메인을 이해하면 더 자연스러운 번역이 가능할 것이라는 판단이 있었다.

> 참고: 이처럼 번역을 여러 단계로 나누는 접근은 관련 연구에서도 찾아볼 수 있다. *Translating Step-by-Step*은 사전 조사, 초안 작성, 수정, 교정으로 번역 과정을 분해한다. 현재 구현과 동일한 절차는 아니지만, 번역 전 분석을 별도 단계로 두는 이유를 설명하는 방법론적 배경이 된다. [Briakou et al., 2024](https://aclanthology.org/2024.wmt-1.123/)

## 4. 용어집을 갱신 가능한 Document Term Memory로 확장했다

Document Term Memory는 원문과 번역어를 나열하는 목록보다 많은 정보를 다룬다. 문서 안에서의 의미, 우선 번역어, 피해야 할 번역어, 혼동하면 안 되는 원문 용어 등을 함께 관리한다.

번역 프롬프트에서는 우선 번역어가 제공된 경우 이를 따르도록 한다. 다만 사전 판단 결과가 `source_meaning_only` 또는 `blocked`이면 번역어를 적용하지 않고 의미 정보만 참고한다. 일관성을 유지하되, 불확실한 번역어가 문서 전체에 퍼지는 상황을 줄이기 위한 구분이다.

번역 이후에는 resolver가 결과와 근거를 검토하고 메모리 갱신을 제안한다. 제안은 허용된 action을 통해 적용한다. 의미 추가, 번역 후보 추가, 우선 번역어 지정, 피해야 할 번역어 지정 같은 변경을 명시적으로 다루는 구조다.

이때 주의해야 할 것은 순환적인 확신이다. 메모리에 있던 번역어를 프롬프트에 넣었고 모델이 그대로 사용했다면, 그 결과만으로 번역어가 올바르다고 다시 확정할 수는 없다. 현재 resolver에는 프롬프트에 주입된 번역어의 영향을 확인하는 정책도 포함되어 있다.

결국 용어 메모리에서 중요했던 것은 저장량보다 **어떤 근거로 번역 판단을 유지하고 바꿀 것인가**였다.

## 5. 긴 문서에는 문맥을 이어주는 메모리를 추가했다

용어 기준을 공유하더라도 문서 앞부분의 설명과 문체를 뒤까지 이어가기가 힘들다는 문제가 남는다. 이를 위해 추가한 것이 `Bilingual Summary Memory`다.

여기서 의미하는 메모리는 하나의 긴 문서를 처리하는 동안 여러 번역 호출을 넘어 유지되는 외부 상태를 뜻한다. 당시 구현은 작업과 문서에 연결된 메모리이며, 해당 작업이 끝나면 삭제되었다. 따라서 여러 문서나 사용자를 가로질러 자동으로 지식을 재사용하는 영구 메모리까지 의미하지는 않았다.

메모리에는 완료된 번역 범위의 원문과 번역문을 누적한다. 압축 기능을 활성화한 경우에는 프롬프트 메모리 limit을 확인하고, limit을 초과하면 기존 요약과 새로 쌓인 내용을 다시 요약한다.

```text
번역 범위 완료
  → 원문·번역문 쌍 누적
  → 압축 활성화 시 메모리 예산 확인
  → 예산 초과 시 누적 요약 갱신
  → 다음 번역 범위에서 참조
```

요약은 원문 내용과 번역문 흐름뿐 아니라 문체, 논의 진행 상태, 아직 해소되지 않은 참조도 담도록 설계했다. 원문에서 무엇을 설명했는지와 번역문에서 어떻게 표현해 왔는지를 함께 전달하려는 의도다.

> 참고: 원문·번역문을 함께 활용하는 다층 메모리의 관련 연구로는 DelTA가 있다. DelTA는 고유명사 기록, 이중 언어 요약, 장기 메모리, 단기 메모리를 구분하고 번역 과정에서 조회·갱신한다. 현재 구현은 이 구조 전체의 재현이 아니라, 용어 관리와 누적 문맥 관리라는 관점에서 비교할 수 있다. [Wang et al., DelTA, ICLR 2025](https://arxiv.org/abs/2410.08143)

## 6. 요약 메모리가 용어 판단을 덮어쓰지 않도록 했다

두 메모리를 함께 사용하면서 각각의 책임도 명확히 했다.

Document Term Memory는 용어의 의미와 번역 기준을 담당한다. Bilingual Summary Memory는 내용 전개와 문체의 연속성을 담당한다.

현재 요약 프롬프트에는 용어 규칙을 만들거나, 번역어를 결정·수정·추천하거나, 원문과 번역어의 대응표를 생성하지 말라는 지침이 들어 있다. 요약이 기존 번역을 압축하는 과정에서 새로운 용어 규칙을 만들면 두 메모리의 지침이 충돌할 수 있기 때문이다.

예를 들어 요약 메모리는 ‘앞 절에서 특정 절차의 개요를 설명했고 이제 예외 조건을 다룬다’는 정보를 남길 수 있다. 해당 절차의 이름을 어떤 한국어 용어로 번역할지는 용어 메모리가 관리한다.

## 7. 병렬 처리에서는 메모리를 언제 갱신할지도 중요했다

문맥을 이어가려면 순서가 중요하지만, 모든 범위를 하나씩 번역하면 처리 시간이 길어질 수 있다. 현재 로컬 변경에서는 여러 범위를 wave로 묶어 처리한 뒤, 완료된 wave의 결과로 요약 메모리를 갱신하는 흐름을 사용한다.

```text
여러 범위를 한 wave로 번역
  → wave 결과 수집
  → 요약 메모리 갱신
  → 다음 wave 번역
```

이 방식에서는 같은 wave 안의 번역 범위가 서로의 최종 결과를 즉시 참고하지는 못한다. 대신 다음 wave는 앞선 wave까지의 누적 정보를 사용할 수 있다. 처리량과 문맥 전달의 세밀함 사이에서 조절할 수 있는 지점을 만든 것이었다.

요약 호출 역시 매번 수행하지 않도록 했다. 압축 기능을 켰더라도 예산에 여유가 있으면 원문·번역문 버퍼를 유지하고 요약 호출을 건너뛴다. 압축 기능이 꺼져 있으면 원시 기록을 누적하는 경로로 동작한다. 따라서 ‘메모리 사용’과 ‘요약 압축 사용’은 별도의 설정이다.

## 8. 품질 개선은 비교 가능한 결과로 확인해야 한다

메모리를 추가했다는 사실만으로 품질이 좋아졌다고 결론 내릴 수는 없다. 잘못된 용어가 더 일관되게 반복될 수도 있고, 요약 과정에서 중요한 정보가 빠질 수도 있다.

당시에는 원문, 번역문, 문맥 범위, 삽입 위치 등의 정보를 반환하는 평가 전용 경로와 메모리·프롬프트 스냅샷 저장 기능을 넣어. 이를 바탕으로 동일한 문서를 다음 조건에서 비교할 수 했다.

| 비교 조건 | 확인할 질문 |
| --- | --- |
| 기준선 | 메모리를 추가하기 전에는 어떤 문제가 있는가? |
| 용어 메모리 적용 | 같은 의미의 용어가 더 안정적으로 번역되는가? |
| 문맥 메모리 추가 | 지시 관계와 문체가 더 잘 이어지는가? |
| 압축 활성화 | 문맥 유지와 추가 호출 비용이 어떻게 달라지는가? |

평가에서는 전체 번역 품질 외에도 용어 정확도, 의미별 용어 일관성, 내용 누락, 문체 연속성, 처리 시간과 토큰 사용량을 함께 볼 필요가 있다.

## 9. 이번 개발에서 배운 점

Doc2Doc 문서 번역 에이전트를 개발하면서 배운 점은 두 가지다. 

첫째는 단순 LLM 호출만으로 주어진 과제를 해결하기 어려웠던 것이다. 앞에서 내린 판단을 다음 번역에 전달하고, 새로운 근거가 나타났을 때 그 판단을 수정할 수 있는 구조가 필요했다.

사전 분석은 문서를 이해하는 출발점을 만들었다. Document Term Memory는 용어 판단을 관리했고, Bilingual Summary Memory는 긴 문서의 내용과 문체를 이어주는 역할을 맡았다. 여기에 갱신 시점과 비용을 조절하는 처리 방식을 더하면서, 번역을 여러 단계가 상태를 공유하는 과정으로 다루게 됐다.

앞으로는 같은 문서를 대상으로 구성 요소를 하나씩 켜고 끄는 비교 실험을 통해, 어떤 메모리가 어떤 오류를 줄이는지 확인하려 한다.

둘째는 굳이 복잡하게 멀티 에이전트로 구성을 하지 않더라도 과제를 수행할 수 있다는 점이었다.

처음에는 메모리 업데이트 등의 기능을 생각하며 자연스럽게 멀티 에이전트를 생각했었는데, 규칙 기반으로 적용해본 결과 사용자가 이용하기에 품질이 떨어지지 않으면서도 소요 시간이 예상보다 줄어드는 효과가 있었다. 

그래서 하나의 과제가 여러 역할을 요구한다고 해서 무조건 멀티 에이전트를 생각할 필요는 없다는 점을 배울 수 있었다.
